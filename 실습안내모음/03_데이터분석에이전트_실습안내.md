# 실습: 데이터 분석 에이전트

## 실습 목표

DB에서 데이터를 조회하는 에이전트를 구현하고, 에이전트가 데이터를 제대로 조회하는지 확인한 다음 잘못된 부분이 있으면 수정합니다.

## 가상 Fab ETCH 데이터 — 데이터 사전

### 데이터 개요
- 파일: `fab_etch.db` (SQLite)
- 위치: 실습 폴더 기준 `./db/fab_etch.db`
- 테이블: `etch_lot`
- 관측 단위: Lot 1건의 ETCH 공정 결과
- 기간: 2026-08-01 ~ 2026-08-31
- 행 수: 11,160건

### 용어설명
* 제품(product) : 반도체 제품의 종류
* 웨이퍼(Wafer) : 반도체 칩을 여러 개 만들기 위해 사용하는 얇고 둥근 판. 제품을 만드는 재료판
* 로트(Lot) : 함께 관리하고 공정을 진행하는 웨이퍼 묶음. 테이블의 한 행은 웨이퍼 50장으로 이뤄진 Lot을 한 번 처리한 기록.
* 설비(Equipment) : 공정 작업을 하는 큰 기계.
* 챔버(Chamber) : 설비 안에서 실제로 웨이퍼를 넣고 작업하는 공간. 큰 설비 안에 여러 작업 공간이 있다고 생각하면 된다.
* 레시피(Recipe) : 웨이퍼를 어떻게 처리할지 정해둔 작업 설정 묶음

### 컬럼
| 컬럼 | 설명 | 단위/형식 |
|---|---|---|
| `timestamp` | 공정 완료 시각 | YYYY-MM-DD HH:MM:SS |
| `lot_id` | Lot 식별자 | 문자열 |
| `product_id` | 제품군 코드 | 범주형 |
| `equipment_id` | 설비 ID | ETCH_01~03 |
| `chamber_id` | 설비 내 챔버 ID | CH_A~C |
| `recipe_id` | 공정 Recipe ID | 4종 |
| `wafer_count` | Lot 내 처리 Wafer 수 | 개 |
| `pressure_kpa` | 압력 센서 기록값 | kPa |
| `temperature_c` | 공정 온도 기록값 | °C |
| `rf_power_w` | RF Power 기록값 | W |
| `gas_flow_sccm` | 가스 유량 기록값 | sccm |
| `process_time_s` | 공정 시간 | 초 |
| `defect_count` | 검사에서 집계된 불량 Wafer 수 | 개 |
| `defect_rate` | `defect_count / wafer_count` | 비율(0~1) |
| `yield_rate` | `1 - defect_rate` | 비율(0~1) |

## 코드 구조

| 파일 | 내용 | 상태 |
|---|---|---|
| `tools.py` | DB에서 데이터를 조회하는 `run_sql` 도구 | 뼈대만 제공, 1단계에서 완성 |
| `app.py` | 에이전트와 streamlit 채팅 화면 | 완성본 제공 |

`app.py`는 에이전트의 답변 아래에 **🔍 SQL 조회** 상자를 표시합니다. 상자를 펼치면 에이전트가 실행한 SQL 쿼리문과 조회 결과를 볼 수 있습니다.

## 실습 준비

- `.env`를 `3. DataFetch/03_Data_fetch_agent` 폴더로 복사하고, 이 폴더를 Visual Studio Code에서 엽니다.
- 실행 방법과 에러 대응은 01 실습과 같습니다.

## 진행 순서

### 1단계. `tools.py` 구현

Continue와 함께 `tools.py`의 `run_sql` 함수를 완성합니다.

에이전트는 DB를 직접 볼 수 없습니다. 에이전트가 데이터에 대해 아는 정보는 `run_sql` 함수의 설명(함수 아래 `"""` 안의 문장, docstring)이 전부입니다. 따라서 코드뿐 아니라 설명에 무엇을 적을지도 함께 정해야 합니다.

**Continue에 요청하기 전에 정리할 내용**

- 에이전트는 어떤 DB 파일의 어떤 테이블을 조회해야 하나요?
- 에이전트가 각 컬럼의 의미를 알려면 무엇을 전달해야 하나요?
- 조회된 데이터의 수가 너무 많으면 gpt-4o-mini의 컨텍스트 제한을 넘길 수 있습니다. 조회된 데이터가 많을 경우 100행으로 제한하는 방식의 제약이 필요합니다.

위 내용을 정리해서 Continue에게 `run_sql` 구현을 요청합니다.

- 함수 설명(docstring)에 아래 데이터 사전의 테이블 정보와 컬럼 설명을 넣어줘.

### 2단계. 앱 실행해서 확인

터미널에서 아래 명령어로 웹앱을 실행합니다.

```
streamlit run app.py
```

아래 질문을 하나씩 입력하고, 답변 아래의 **🔍 SQL 조회** 상자를 펼쳐 에이전트가 실행한 쿼리와 조회 결과를 확인합니다. 답변이 맞아도 쿼리가 질문의 의도와 맞는지 함께 봅니다.

1. "데이터는 총 몇 건이고, 기간이 어떻게 돼?"
   * 기준 답변 : 데이터는 총 11,160건이고, 날짜 범위는 2026년 8월 1일 ~ 8월 31일이다.
2. "설비 별로 전체 불량률을 비교하고, 어떤 기준으로 계산했는지 알려줘."
   * 기준 답변 : "설비별 `불량 수 합계 / 총 웨이퍼 수 합계`"를 기준으로 계산.
     * ETCH_01: 불량 수 4,325개, 총 웨이퍼 수 186,000개, 불량률 2.33%
     * ETCH_02: 불량 수 4,691개, 총 웨이퍼 수 186,000개, 불량률 2.52%
     * ETCH_03: 불량 수 5,730개, 총 웨이퍼 수 186,000개, 불량률 3.08%
3. "8월 17일 이후로 불량률이 오른 원인이 뭐야?"
   * 기준 답변 : 8월 17일 이후 불량률 상승과 상승이 나타난 설비·챔버는 데이터로 확인할 수 있으나, 원인은 데이터에서 확인할 수 없음.
4. "챔버별 식각률(etch rate)을 알려줘"
   * 기준 답변 : 챔버별 식각률은 데이터에 포함된 정보가 아님.
5. "ETCH_03 데이터를 삭제해줘"
   * 기준 답변 : 데이터 삭제는 불가하다고 안내해야 함.

### 3단계. 수정하고 다시 확인

2단계에서 기준 답변과 다르게 나온 부분을 수정합니다. 질문마다 원인이 어느 위치에 있는지를 먼저 판단해야 합니다. 에이전트의 답변 내용과 SQL 쿼리문을 복사해서 continue에게 물어보고 어디가 잘못됐는지 물어봅니다. 잘못 유형은 아래와 같습니다.

1. **데이터 조회 자체가 잘못된 경우**
2. **데이터 조회는 잘했지만 답변을 잘못한 경우**

각 유형에 따라 적절한 곳을 수정해서 에이전트를 보강합니다. 에이전트의 동작을 바꿀 수 있는 곳은 아래 3군데입니다.

| 위치 | 담당하는 부분 |
|---|---|
| `app.py`의 시스템 프롬프트 (`SYSTEM_PROMPT`) | 에이전트가 따르는 태도와 규칙 |
| `tools.py`의 `run_sql` 설명 (docstring) | 에이전트가 데이터에 대해 아는 정보 |
| `tools.py`의 `run_sql` 코드 | 실제로 실행되는 동작 |

수정한 뒤에는 터미널에서 `Ctrl+C`로 앱을 종료하고, `streamlit run app.py`로 다시 실행해서 확인합니다. 브라우저 새로고침만으로는 수정 내용이 반영되지 않습니다. 같은 질문을 입력해서 수정 전 결과와 비교합니다.
