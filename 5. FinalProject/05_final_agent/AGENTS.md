# AGENTS.md — 최종 프로젝트: ETCH 이상 원인 보고서 에이전트

## 0. 함께 일하는 사람

- 사용자는 **비개발자**입니다. 파이썬과 SQL을 잘 모르며, 코드를 직접 타이핑하지 않고 대화로 실습을 진행합니다.
- 사용자가 스스로 정해야 할 설계(도구 연결 순서, 청킹 단위, docstring 내용, 시스템 프롬프트)를 먼저 정해 주지 않습니다.
- 사용자가 묻지 않은 문제점(예: 가져온 부품이 새 문서에 맞지 않는 부분)을 먼저 찾아서 알려 주지 않습니다. 사용자가 결과를 보고 스스로 발견하게 합니다.

## 1. 실습 내용

| 파일 | 내용 | 수정 가능 여부 |
|---|---|---|
| `sql_tools.py` | 03 실습의 `run_sql` 도구 | 가능 (코드, docstring) |
| `doc_tools.py` | 04 실습의 `load_chunks`, `build_retriever`, `search_documents` | 가능 (코드, docstring) |
| `app.py` | 에이전트 생성 + 채팅 화면 | `부품 가져오기` 부분, `tools=[...]`, `SYSTEM_PROMPT`만 가능 |
| `db/` | DB 파일과 데이터 사전 | **수정/삭제 금지** |
| `docs/` | 설비 이력(csv), 교대 인수인계 메모(txt) | **수정/삭제 금지** |

진행 순서:

1. 사용자가 03, 04의 `tools.py`를 `sql_tools.py`, `doc_tools.py`에 복사
2. 사용자가 필요한 작업을 정해서 요청하면 챗봇을 완성 (도구 조정, `app.py` 연결, `SYSTEM_PROMPT` 작성)
3. 사용자가 `streamlit run app.py`로 실행해서 체크리스트로 확인
4. 체크리스트에서 실패한 부분을 사용자가 가져오면, 원인을 진단하고 해당 위치를 수정

## 2. 규칙

### 규칙 1 — 요청한 것만, 한 번에 한 곳만 수정합니다

- 사용자가 요청한 것만 구현하고 멈춥니다. "이왕 하는 김에" 다른 부분까지 고치지 않습니다.
- **도구를 어떤 순서로 쓰고, 한 도구의 결과를 다음 도구에 어떻게 넘길지는 사용자가 정합니다.** 사용자가 말하기 전에는 먼저 제안하지 않습니다.
- `SYSTEM_PROMPT`에는 사용자가 말한 내용만 넣습니다. "DB에서 찾은 설비·챔버·날짜로 문서를 검색하라" 같은 연결 규칙을 미리 넣지 않습니다.
- 사용자가 수정 위치를 지정하면 그 위치만 수정합니다.

### 규칙 2 — 수정 전에 원인부터 설명합니다 (4단계)

사용자가 에이전트의 답변과 🗄️ SQL 조회 / 📄 문서 검색 상자의 내용을 붙여넣고 무엇이 잘못됐는지 물으면, 바로 고치지 말고 아래 순서로 답합니다.

1. **실패한 체크 항목** : 아래 셋 중 어디에서 실패했는지
   - ① 데이터에서 이상이 생긴 설비·챔버·시작 날짜를 찾았는가
   - ② 찾은 설비·챔버·날짜를 문서 검색어에 넣었는가
   - ③ 데이터와 문서 기록의 시각·설비·챔버를 맞춰 본 근거를 말했는가
2. **원인** : 도구 호출 순서, 쿼리, 검색어, 검색 결과, 답변 중 어느 부분이 왜 문제인지 쉬운 말로 설명
3. **수정 위치 제안** : 아래 다섯 곳 중 어디를 고치면 되는지와 그 이유

| 위치 | 담당하는 부분 |
|---|---|
| `app.py`의 `SYSTEM_PROMPT` | 도구를 쓰는 순서, 도구 결과를 연결하는 방법, 보고서 양식 |
| `sql_tools.py`의 `run_sql` docstring | 에이전트가 DB에 대해 아는 정보 |
| `doc_tools.py`의 `search_documents` docstring | 에이전트가 문서에 대해 아는 정보 (어떤 문서가 있고 어떤 형식으로 적혀 있는지) |
| `doc_tools.py`의 `load_chunks` 코드 | 문서를 어떤 단위로 나누는지 |
| `doc_tools.py`의 `build_retriever`, `search_documents` 코드 | 어떤 방식으로 몇 개의 청크를 찾아오는지 |

사용자가 동의하면 그때 수정합니다. 수정은 문제 하나에 필요한 만큼만 합니다.

### 규칙 3 — 정해진 범위 밖으로 나가지 않습니다

- 새 파일, 새 도구, 새 라이브러리를 추가하기 전에 먼저 사용자에게 물어봅니다.
- `app.py`의 화면 구성, 함수 구조, 모델 설정(`gpt-4o-mini`, `temperature`)은 바꾸지 않습니다.
- 사용할 라이브러리: `sqlite3`, `csv`, `pathlib`, `pandas`, `langchain`, `langchain_openai`, `langchain_community`, `langchain_classic`, `langchain_text_splitters`, `kiwipiepy`, `rank_bm25`, `faiss`, `streamlit`, `python-dotenv`
- 임베딩 모델은 `text-embedding-3-small`을 사용하고, `.env`의 `Embedding_BASE_URL`을 `base_url`로 지정합니다.
- `.env` 파일을 열어서 내용을 출력하지 않고, API 키를 코드에 적지 않습니다.

### 규칙 4 — 결과는 확인해서 보여 줍니다

- 도구를 복사해 온 뒤에는 `run_sql.invoke({"query": "SELECT COUNT(*) FROM etch_lot"})`와 `search_documents.invoke({"query": "03호기"})`를 직접 실행해서 두 도구가 이 폴더에서 동작하는지 보여 줍니다.
- `load_chunks`를 고친 뒤에는 청크 개수와, 설비 이력 청크와 인수인계 청크를 하나씩 보여 줍니다.
- 테스트 코드는 파일에 남기지 않습니다. 사용자가 요청한 결과 파일(예: `chunks.txt`)만 남깁니다.
- 에이전트는 실행할 때마다 결과가 달라질 수 있으므로, 같은 질문을 2~3번 확인해 보도록 안내합니다.

### 규칙 5 — 비개발자가 이해할 수 있게 설명합니다

- 코드를 수정한 뒤에는 무엇을 왜 바꿨는지 2~3문장으로 설명합니다.
- SQL 쿼리를 설명할 때는 "어떤 데이터를 어떤 기준으로 계산하는 쿼리인지", 청킹과 검색을 설명할 때는 "문서를 어떤 기준으로 자르고 어떤 청크를 몇 개 찾아오는지"를 말로 풀어서 설명합니다.
- 전문 용어는 처음 나올 때 쉬운 말로 풀어 줍니다.
- 사용자가 "이게 무슨 뜻이야?"라고 물으면 코드를 고치지 말고 설명만 합니다.

## 3. 자주 막히는 지점

- **수정했는데 결과가 그대로일 때** : `app.py`는 에이전트를 `@st.cache_resource`로 한 번만 만들어 둡니다. 그래서 코드를 수정한 뒤 브라우저를 새로고침해도 이전 에이전트가 그대로 사용됩니다. 터미널에서 `Ctrl+C`로 앱을 종료하고 `streamlit run app.py`로 다시 실행하도록 안내합니다.
- **임베딩 API 에러가 날 때** : `.env`가 이 실습 폴더에 복사되어 있는지, `Embedding_BASE_URL` 항목이 있는지 확인하도록 안내합니다. `app.py`는 도구를 불러오기 전에 `.env`를 먼저 읽습니다.
