# AGENTS.md — RAG 에이전트 실습

## 0. 함께 일하는 사람

- 사용자는 **비개발자**입니다. 파이썬을 잘 모르며, 코드를 직접 타이핑하지 않고 대화로 실습을 진행합니다.
- 이 실습의 목표는 완성된 앱이 아니라, **사용자가 에이전트의 문제를 직접 발견하고 어디를 고쳐야 하는지 판단하는 연습**입니다.
- 따라서 사용자가 스스로 찾아야 할 문제를 먼저 찾아서 고쳐 주지 않습니다.

## 1. 실습 내용

`docs/` 폴더의 문서(반도체 8대 공정 설명 txt 9개, 첨단패키징 보도자료 md 1개)를 검색해서 질문에 답하는 Streamlit 챗봇입니다.

| 파일 | 내용 | 수정 가능 여부 |
|---|---|---|
| `tools.py` | 문서를 청크로 나누는 `load_chunks`, 검색기를 만드는 `build_retriever`, 검색 도구 `search_documents` | 가능 (코드, docstring) |
| `app.py` | 에이전트 생성 + 채팅 화면 | `SYSTEM_PROMPT`만 가능 |
| `docs/` | 검색 대상 문서 | **수정/삭제 금지** |

## 2. 규칙

### 규칙 1 — 요청한 것만, 한 번에 한 곳만 수정합니다

- 사용자가 요청한 것만 구현하고 멈춥니다. "이왕 하는 김에" 다른 부분까지 고치지 않습니다.
- 청킹 방식(분할 기준, 청크 크기, 겹침, 제목 정보 붙이기 등)과 검색 방식(BM25/Dense/Hybrid, 비중, 가져올 개수)은 **사용자가 정한 대로** 구현합니다. 사용자가 정하지 않은 부분이 있으면 임의로 정하지 말고 먼저 물어봅니다.
- 사용자가 요청하지 않은 개선(시스템 프롬프트 규칙 추가, 청크 크기 조정 등)을 미리 넣지 않습니다. 이것들은 사용자가 4단계에서 문제를 발견하고 요청해야 하는 내용입니다.
- 사용자가 수정 위치를 지정하면 그 위치만 수정합니다.

### 규칙 2 — 수정 전에 원인부터 설명합니다 (4단계)

사용자가 에이전트의 답변이나 검색 결과를 붙여넣고 무엇이 잘못됐는지 물으면, 바로 고치지 말고 아래 순서로 답합니다.

1. **잘못된 유형** : 필요한 청크를 검색해 오지 못했는지, 검색은 맞았지만 답변이 잘못됐는지
2. **원인** : 검색 결과나 답변의 어느 부분이 왜 문제인지 쉬운 말로 설명
3. **수정 위치 제안** : 아래 네 곳 중 어디를 고치면 되는지와 그 이유

| 위치 | 담당하는 부분 |
|---|---|
| `app.py`의 `SYSTEM_PROMPT` | 에이전트가 따르는 태도와 규칙 |
| `tools.py`의 `search_documents` docstring | 에이전트가 이 도구로 무엇을 찾을 수 있는지 |
| `tools.py`의 `load_chunks` 코드 | 문서를 어떤 단위로 나누는지 |
| `tools.py`의 `build_retriever`, `search_documents` 코드 | 어떤 방식으로 몇 개의 청크를 찾아오는지 |

사용자가 동의하면 그때 수정합니다. 수정은 문제 하나에 필요한 만큼만 합니다.

### 규칙 3 — 정해진 범위 밖으로 나가지 않습니다

- 새 파일, 새 도구, 새 라이브러리를 추가하기 전에 먼저 사용자에게 물어봅니다.
- `app.py`의 화면 구성, 함수 구조, 모델 설정(`gpt-4o-mini`, `temperature`)은 바꾸지 않습니다.
- 사용할 라이브러리: `pathlib`, `langchain`, `langchain_openai`, `langchain_community`, `langchain_classic`, `langchain_text_splitters`, `kiwipiepy`, `rank_bm25`, `faiss`, `streamlit`, `python-dotenv`
- 임베딩 모델은 `text-embedding-3-small`을 사용하고, `.env`의 `Embedding_BASE_URL`을 `base_url`로 지정합니다.
- `.env` 파일을 열어서 내용을 출력하지 않고, API 키를 코드에 적지 않습니다.

### 규칙 4 — 결과는 확인해서 보여 줍니다

- `load_chunks`를 구현한 뒤에는 청크 개수와 청크 몇 개의 앞부분을 직접 실행해서 보여 줍니다.
- `search_documents`를 구현한 뒤에는 간단한 검색어(예: `"웨이퍼"`)로 `search_documents.invoke({"query": ...})`를 직접 실행해 결과를 보여 줍니다.
- 테스트 코드는 파일에 남기지 않습니다. 사용자가 요청한 결과 파일(예: `chunks.txt`)만 남깁니다.
- 수정한 뒤에는 "고쳤습니다"로 끝내지 말고, 사용자가 같은 질문으로 다시 확인하도록 안내합니다.
- 에이전트는 실행할 때마다 결과가 달라질 수 있으므로, 같은 질문을 2~3번 확인해 보도록 안내합니다.

### 규칙 5 — 비개발자가 이해할 수 있게 설명합니다

- 코드를 수정한 뒤에는 무엇을 왜 바꿨는지 2~3문장으로 설명합니다.
- 청킹이나 검색 설정을 설명할 때는 "문서를 어떤 기준으로 자르는지", "어떤 청크를 몇 개 찾아오는지"를 말로 풀어서 설명합니다.
- 전문 용어는 처음 나올 때 쉬운 말로 풀어 줍니다.
- 사용자가 "이게 무슨 뜻이야?"라고 물으면 코드를 고치지 말고 설명만 합니다.

## 3. 자주 막히는 지점

- **수정했는데 결과가 그대로일 때** : `app.py`는 에이전트를 `@st.cache_resource`로 한 번만 만들어 둡니다. 그래서 `SYSTEM_PROMPT`나 `tools.py`를 수정한 뒤 브라우저를 새로고침해도 이전 에이전트가 그대로 사용됩니다. 터미널에서 `Ctrl+C`로 앱을 종료하고 `streamlit run app.py`로 다시 실행하도록 안내합니다.
- **문서를 찾지 못할 때** : 터미널의 현재 위치가 이 실습 폴더인지 확인합니다. `DOCS_DIR`은 실행 위치 기준 상대경로입니다.
- **임베딩 API 에러가 날 때** : `.env`가 이 실습 폴더에 복사되어 있는지, `Embedding_BASE_URL` 항목이 있는지 확인하도록 안내합니다. `app.py`는 `tools`를 불러오기 전에 `.env`를 먼저 읽습니다.
- **앱 시작이 느릴 때** : 앱이 시작될 때 모든 청크를 임베딩하고 형태소 분석기를 불러오므로 첫 실행에 시간이 걸립니다.
